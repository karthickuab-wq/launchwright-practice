## The user's tap to send (open point O5)

- **Any workflow can be started by hand only with Expo's command-line tool or its REST API** ("You can also start any workflow manually with `eas workflow:run` or the REST API, regardless of the `on` key"). Both need an Expo sign-in or token. Expo's website has no button to start a new run; it can re-run a finished one. Sources: [Workflows syntax](https://docs.expo.dev/eas/workflows/syntax.md), "on"; [Manage workflow runs](https://docs.expo.dev/eas/workflows/manage-workflow-runs.md), "Re-run a workflow".
- **A require-approval job** pauses a run ("Action required") until "a user can approve or reject", which "translates to success or failure of the job". Approve within 30 days of the run's start, or the run fails before its next job. Jobs after approval run with the access of whoever started the run, not the approver's. Expo's own example puts it before a production web deploy. Source: [Pre-packaged jobs](https://docs.expo.dev/eas/workflows/pre-packaged-jobs.md), "Require Approval"; [Manage workflow runs](https://docs.expo.dev/eas/workflows/manage-workflow-runs.md), "Workflow run statuses".
- **A run's page** is on the project's workflows page on expo.dev; it shows each job, its logs and its outputs, and a run can be cancelled there ("Cancel workflow"). Source: [Manage workflow runs](https://docs.expo.dev/eas/workflows/manage-workflow-runs.md).
- **A push can't skip the marker:** `on.push.if` decides whether a run starts, and can read `github.commit_message`; `[eas skip]`, `[skip eas]` or `[no eas]` in a message skips push runs. Source: [Workflows syntax](https://docs.expo.dev/eas/workflows/syntax.md), "on.push".
- **Pull request triggers run the pull request's own workflow files** ("a pull request can change the workflow that its own run uses"), which is why no Launchwright workflow starts on one. Source: the same page, "on.pull_request".
- **Not checked:** whether the approve button works in a phone's browser, and whose access a run started by a GitHub push uses after approval. Both are for the practice run (P3.Z's tries).

## Store builds and versions

- **The `production` profile** is the store build: Android makes an app bundle (.aab) by default, which Google needs; iOS is signed for the App Store. `eas build` without `--profile` uses `production`. Sources: [Configure Expo Build with eas.json](https://docs.expo.dev/build/eas-json.md), "Production builds"; [Submit to Google Play](https://docs.expo.dev/submit/android.md), "Build a production app".
- **Build numbers:** with `cli.appVersionSource` "remote" and `autoIncrement: true` on the production profile, Expo's servers count up the developer-facing build number on every build. The user-facing `version` in app.json is set by hand for each store release. Source: [App version management](https://docs.expo.dev/build-reference/app-versions.md).
- **Builds without questions need a first run with questions:** "Run `eas build -p [all|android|ios]` from your local terminal for each platform you want to support on CI", so the tool can ask for what it needs; build credentials must exist first. An App Store Connect API key lets Expo repair iOS credentials later. Source: [Trigger builds from CI](https://docs.expo.dev/build/building-on-ci.md).

## Sending to Apple

- **What it needs:** a paid Apple Developer account; the app's App Store Connect Apple ID as `ascAppId` in the submit profile (needed when nothing can be asked); and, for workflows, an App Store Connect API key set up for Expo Submit, through `eas credentials --platform ios`: the `production` profile, then "App Store Connect: Manage your API Key", then "Set up your project to use an API Key for Expo Submit". Source: [Submit to the Apple App Store](https://docs.expo.dev/submit/ios.md).
- **Finding ascAppId:** App Store Connect, Apps, the app, the App Store tab, General, App Information: "Apple ID" under General Information. Source: the same page, "How to find ascAppId".
- **What a submission does:** uploads the build to App Store Connect, where it appears in TestFlight after processing ("usually 10-15 minutes"). "To release to production, log in to App Store Connect and submit the build for App Review." Source: the same page.
- **Submitting for review** (Account Holder, Admin or App Manager): Apps, the app, the version in the sidebar; in the Build section tap the add button (+), pick the build, Done, Save (a build marked Missing Compliance needs its export compliance answers first); then "Add for Review" at the top right, and "Submit for Review". The status goes to In Review. Sources: [Choose a build to submit](https://developer.apple.com/help/app-store-connect/manage-builds/choose-a-build-to-submit), [Submit an app](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/submit-an-app).
- **Making the app's entry:** Apps, the add button (+) at the top left, New App; pick the platforms and enter the app's details; choose Limited or Full Access; Create. The Account Holder must have signed the latest agreement in Business first. Its status is then Prepare for Submission. Source: [Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app).
- **App information fields:** Name (2 to 30 characters), Subtitle (30), Privacy Policy URL (required for iOS), Bundle ID (fixed once a build is uploaded), SKU (letters, numbers, hyphens, periods and underscores; fixed), Category, Age Rating (required), Content Rights. Source: [App and compliance information](https://developer.apple.com/help/app-store-connect/reference/app-information/app-information).
- **Version fields:** Screenshots (required), Promotional Text (170, optional), Description (4,000, plain text, required), Keywords (up to 100 bytes, each over two characters, no other apps' names, required), Support URL (must lead to real contact details, required), Marketing URL (optional), Copyright (required, such as "2026 Example, Inc."), Version Release (Manual, Automatic, or Automatic no earlier than a date), What's New (not on the first version, required after), App Review Information (contact name, email and phone in international format, and notes). Source: [Platform version information](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information).
- **Screenshots:** at least one, up to 10 per device size, .jpeg, .jpg or .png, no transparency. Required: iPhone with Dynamic Island, medium display (1179 × 2556 or 1206 × 2622 portrait), and iPad 13-inch if the app runs on iPad. Screenshots for the highest required size are scaled down for smaller ones. Source: [Screenshot specifications](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications).

## Sending to Google

- **What it needs:** a Google Play developer account; the app made in Play Console ("Create app"); and a Google service account key, made by following Expo's guide and uploaded on Expo's website: the project, Credentials, Android, the app's Application identifier, Service credentials, "Add a Google service account key", "Upload new key", Save. Expo keeps it on the Expo account; another app can use the same key with "Choose saved key". Source: [Submit to the Google Play Store](https://docs.expo.dev/submit/android.md), "Prerequisites".
- **The first upload** "creates your app's first release on the internal testing track"; the app stays a draft in Play Console until its store listing and setup tasks are done. Source: the same page, "First-time submission".
- **Submit profile options:** `track` is production, beta, alpha or internal; `releaseStatus` is completed, draft, halted or inProgress; `rollout` works only with inProgress; `changesNotSentForReview` holds changes until sent for review in Play Console. Source: [eas.json reference](https://docs.expo.dev/eas/json.md), Android submit options. Launchwright uses only `internal`, so moving a version on is always the user's step in Play Console.
- **Creating the app:** Play Console, Create app; the name, the default language, app or game, free or paid, a contact email; tick the Developer Program Policies and US export laws declarations and accept the Play App Signing terms; Create app. Package names are permanent. Source: [Create and set up your app](https://support.google.com/googleplay/android-developer/answer/9859152).
- **Store listing:** Grow users, Store presence, Store listings: App name (30), Short description (80), Full description (4,000). An app icon (32-bit PNG, 512 × 512, up to 1,024 KB) and a feature graphic (JPEG or 24-bit PNG, 1024 × 500) are required; up to 8 screenshots per device type; no "Best", "#1", "Free" or prices in graphics. Sources: the same page, "Add product details"; [Add preview assets](https://support.google.com/googleplay/android-developer/answer/9866151).
- **App content:** a privacy policy, ads, app access (instructions for reviewers), target audience and content, sensitive permissions, content ratings, and data safety. Source: [Prepare your app for review](https://support.google.com/googleplay/android-developer/answer/9859455).
- **Moving a version to another track:** on the track's page (Test and release, Testing, Closed testing, then Manage track; or Production), "Create new release", then "Add from library" to use a version already uploaded; name it, add release notes, Next, then roll it out. "Create new release" stays off until the Dashboard's setup tasks are done. Source: [Prepare and roll out a release](https://support.google.com/googleplay/android-developer/answer/9859348).

## Google's tester rule

- Personal accounts made after Nov 13, 2023 "must run a closed test for their app with a minimum of 12 testers who have been opted in continuously for at least 14 days", then apply for production access on the Dashboard ("Apply for production"), answering three parts: about the closed test, about the app, about production readiness. Review "usually takes seven days or less". Closed testing needs the app setup done first. Source: [App testing requirements for new personal developer accounts](https://support.google.com/googleplay/android-developer/answer/14151465).
- **Testers:** on the closed test's Testers tab, an email list (up to 2,000 per list) or Google Groups; a feedback email or link; then "Copy the shareable link" for testers to opt in. Someone already in the internal test must leave it to join a closed test. Testers must buy a paid app in a closed test. Source: [Set up an open, closed, or internal test](https://support.google.com/googleplay/android-developer/answer/9845334).

## Rolling back and updating

- **Web apps on Expo Hosting:** deployments never change; moving an alias or the production address to an older deployment is a rollback, done with `eas deploy:alias --prod --id=<deployment>`, a command-line step. A deploy job with `prod: true` puts the run's own build at the production address. Sources: [Deployments and aliases](https://docs.expo.dev/eas/hosting/deployments-and-aliases.md); [Workflows syntax](https://docs.expo.dev/eas/workflows/syntax.md), the deploy job.
- **Over-the-air updates** need Expo's update service set up in the app (`eas update:configure`, then new builds). A rollback re-publishes an earlier update, or tells phones to use the one built into the app, with `eas update:rollback`, an interactive command. A workflow's `update` job publishes an update, and `update-rollout` widens a partial one; Expo's own example waits for a require-approval job before 100%. Sources: [Rollbacks](https://docs.expo.dev/eas-update/rollbacks.md) (page dated Nov 2, 2026); [Pre-packaged jobs](https://docs.expo.dev/eas/workflows/pre-packaged-jobs.md), "Update" and "Update rollout".
- **A version installed from a store can't be pulled back:** Apple and Google serve the new version; a fix goes out as a new version (spec section 7, choice 13).
